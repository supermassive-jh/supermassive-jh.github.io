[지난 글](/post/nextjs-bff-frontend)까지 Spring + Next.js BFF 구조를 다 붙였다. 이 글은 그걸 실제로 검증하면서 나온 트러블슈팅과, 아직 안 끝난 TODO들을 정리하는 마지막 편이다.

## 검증한 것들

curl로 API 레벨을 먼저 확인했다.

- `/api/auth/login` — 틀린 비밀번호는 401, 정상 로그인은 200과 함께 `JSESSIONID` 발급.
- 발급된 쿠키로 `/api/auth/me` 호출 시 200.
- `/api/auth/logout` 호출 후 재호출 시 403.
- `/api/join` — 최초 가입 201, 동일 이름으로 재가입 시 409.

그다음 브라우저(시크릿 창)로 실제 흐름을 확인했다.

- `/member`에 직접 접근 — 미로그인이면 `/login`으로 리다이렉트, 로그인 후 접근하면 정확한 이름 표시.
- `/admin` — 전체 회원 목록이 정상 표시되고, 로그아웃 버튼도 정상 동작.
- 회원가입 → 로그인 → 보호된 페이지 접근 → 로그아웃까지, 전체 사이클을 브라우저로 최종 확인.

API 레벨 확인과 브라우저 확인을 나눈 이유는 단순하다. curl은 헤더/쿠키/상태 코드를 정확하게 볼 수 있어서 서버 쪽 로직을 검증하기 좋고, 브라우저는 실제 리다이렉트 체인과 화면 상태까지 확인할 수 있어서 서로 보완이 된다.

## 트러블슈팅

**Windows `cmd.exe`의 작은따옴표 문제.** `curl -d '{"a":"b"}'`처럼 작은따옴표를 쓰면, `cmd.exe`는 이걸 특수문자로 처리하지 않고 그대로 바디에 포함시켜버려서 JSON이 깨진다. 큰따옴표를 이스케이프해서(`-d "{\"a\":\"b\"}"`) 해결했다. bash에 익숙해져 있으면 꼭 한 번은 걸리는 부분이다.

**서버 재시작 없이 테스트했던 문제.** `SecurityConfig`를 고쳤는데, 재시작 전 프로세스로 테스트하다가 옛날 규칙(`/api/auth/login`이 아직 `permitAll`에 없던 상태)대로 동작하는 걸 보고 한참 헤맸다. 익명 사용자가 `authenticated()`가 필요한 경로에 접근하면 401이 아니라 **403**이 뜨는데, 이건 `AnonymousAuthenticationFilter`가 익명 사용자를 "인증된 상태"로 취급하기 때문에 인가 실패가 403으로 나타나는 것이다. 재시작하니 바로 해결됐다 — 설정을 고쳤는데 동작이 이상하면 일단 재시작부터 의심하는 습관이 붙었다.

**로그인 폼이 GET 쿼리스트링으로 제출됐던 사례.** 파일을 저장하기 전 상태였거나 브라우저가 이전 버전을 캐싱했던 것으로 추정된다. 이후엔 정상적으로 POST + Server Action으로 동작하는 걸 확인했다.

**로그아웃 쿠키 이름 오타** — [지난 글](/post/nextjs-bff-frontend)에서 다룬, 서버 세션이 실제로는 안 죽는 조용한 버그. 화면만 보고 "로그아웃 성공"이라고 판단하면 안 되는 이유가 됐다.

## 남은 TODO / 알려진 제약

- 회원가입 화면에서 `role`을 사용자가 직접 선택할 수 있는 상태다. 실서비스라면 권한 상승 취약점이 되므로, 서버에서 강제로 `role=user`로 고정하거나 별도 관리자 승인 절차가 필요하다.
- Spring 쪽 예전 Thymeleaf 컨트롤러(`MainController`, `MemberController`의 뷰 매핑)와 템플릿(`*.html`), `spring-boot-starter-thymeleaf` 의존성이 아직 정리되지 않은 채 남아있다.
- 세션은 현재 Spring 서버 인메모리에 저장된다. 서버를 여러 대로 늘리면 Redis 기반 Spring Session으로 외부화해야 한다.
- `name` 컬럼에 DB `unique` 제약이 없어서, 애플리케이션 레벨 중복 체크(`existsByName`)만으로는 동시 가입 시 레이스 컨디션 가능성이 남아있다.

> Thymeleaf로 화면까지 서버가 직접 그리던 구조에서, Next.js가 화면을 맡고 Spring이 순수 API 서버로 물러나는 구조로 옮기는 과정을 다섯 편에 걸쳐 정리했다. 핵심은 결국 하나였다 — **인증 방식(세션)은 그대로 두고, "누가 화면을 그리는가"만 바꿨다.** 무리하게 JWT로 갈아타지 않은 게, 지금 돌아봐도 이 규모에는 맞는 선택이었다.
